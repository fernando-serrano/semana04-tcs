Tema de la semana

Esta semana abordamos dos ideas que van juntas: el testing, como el conjunto de actividades que ejecutan el software para detectar defectos, y la calidad de software, como el grado en que el producto cumple las necesidades de quienes lo usan y los requisitos definidos.

El testing es una de las herramientas para medir y construir calidad, pero no la única: la calidad también se trabaja en el diseño, en las revisiones de código y en el proceso de desarrollo.

¿Qué es el testing?

El testing (o pruebas de software) es el proceso de verificar que un programa funciona como se espera. Consiste en ejecutar código bajo distintas condiciones para detectar errores antes de que lleguen a producción, asegurando calidad, confiabilidad y una mejor experiencia para quien usa el software.

Tipos de testing

Pruebas unitarias

Verifican piezas pequeñas de código de forma aislada, como una función o un método.

Pruebas de integración

Comprueban que distintos módulos o servicios funcionen correctamente en conjunto.

Pruebas end-to-end

Simulan el flujo completo de un usuario real, de principio a fin, sobre la aplicación.

Pruebas manuales

Exploración directa por parte de una persona para encontrar problemas no cubiertos por scripts.

¿Por qué es importante?

Testear reduce costos a largo plazo al detectar errores temprano, facilita hacer cambios con confianza y mejora la calidad general del producto. Un buen conjunto de pruebas actúa como red de seguridad para el equipo de desarrollo.

Módulo · Calidad

Calidad de Software

Qué entendemos por calidad, cómo se mide, qué atributos la componen y qué prácticas del día a día ayudan a construirla.

Definición

La calidad de software es el grado en que un producto de software satisface los requisitos establecidos y las necesidades reales de sus usuarios. No se limita a "que no tenga errores": incluye que sea usable, mantenible, seguro y suficientemente rápido para el contexto en que se usa.

Se distinguen dos miradas complementarias: la calidad del producto (cómo es el software que se entrega) y la calidad del proceso (cómo se construye ese software).

Atributos de calidad

Modelos como la norma ISO/IEC 25010 describen la calidad a través de características medibles. Estas son las más usadas:

Funcionalidad

El software hace lo que se espera: es completo, correcto y apropiado para la tarea.

Fiabilidad

Se mantiene disponible y se comporta de forma estable, incluso ante fallos.

Usabilidad

Es comprensible y fácil de operar para el usuario al que está dirigido.

Eficiencia

Responde en tiempos aceptables usando de forma razonable los recursos disponibles.

Mantenibilidad

Puede modificarse, corregirse y extenderse sin un costo desproporcionado.

Portabilidad

Puede adaptarse e instalarse en distintos entornos con poco esfuerzo.

Seguridad

Protege la información y controla quién puede acceder a qué y para qué.

Compatibilidad

Coexiste e intercambia información correctamente con otros sistemas.

Aseguramiento vs. control de calidad

QA — Aseguramiento

Orientado al proceso y a la prevención: definir estándares, plantillas, revisiones y flujos de trabajo para que los defectos no lleguen a aparecer.

QC — Control

Orientado al producto y a la detección: ejecutar pruebas e inspecciones sobre lo construido para encontrar los defectos que ya existen.

Testing

Es la actividad concreta dentro del control de calidad: ejecutar el software con casos de prueba para comparar el resultado real con el esperado.

Métricas de calidad

  • Cobertura de pruebas: porcentaje del código ejercitado por las pruebas automatizadas.
  • Densidad de defectos: defectos encontrados por tamaño del módulo o por funcionalidad.
  • Defectos escapados: errores detectados en producción y no durante el desarrollo.
  • Tiempo medio de corrección: cuánto tarda el equipo en resolver un defecto reportado.
  • Deuda técnica: esfuerzo pendiente acumulado por atajos tomados en el diseño o el código.
  • Complejidad ciclomática: número de caminos de ejecución; a mayor complejidad, mayor riesgo.

Buenas prácticas

  • Requisitos claros y verificables: si no se puede comprobar, no se puede asegurar.
  • Revisiones de código: una segunda lectura detecta lo que las pruebas no cubren.
  • Pruebas automatizadas: permiten cambiar el código sin miedo a romper lo que ya funcionaba.
  • Integración continua: validar cada cambio de forma automática al integrarlo.
  • Estándares de codificación: un estilo común hace el código más legible y mantenible.
  • Documentación mínima y viva: lo suficiente para entender el sistema, y actualizada.
  • Mejora continua: revisar el proceso periódicamente y ajustar lo que no funciona.

El costo de la calidad

Cuanto más tarde se detecta un defecto, más cuesta corregirlo. Un error hallado durante el análisis se resuelve reescribiendo una frase; el mismo error detectado en producción puede implicar corregir código, migrar datos, desplegar una nueva versión y atender el impacto en los usuarios.

Por eso invertir en calidad de forma temprana —requisitos claros, revisiones y pruebas desde el inicio— no es un gasto adicional, sino una reducción del costo total del proyecto.

Módulo · Proceso

Proceso de Testing

Cómo se organiza el trabajo de pruebas en la práctica: sus etapas, las técnicas para diseñar casos de prueba y las herramientas más usadas.

Ciclo de vida del testing

El testing no es un paso único al final del desarrollo: es un proceso con etapas propias que se repiten en cada iteración del proyecto.

1. Planificación

Se define el alcance, los objetivos, los recursos y la estrategia general de pruebas.

2. Diseño

Se elaboran los casos de prueba a partir de los requisitos y los criterios de aceptación.

3. Ejecución

Se corren los casos de prueba, manual o automáticamente, y se registran los resultados.

4. Cierre

Se analizan los resultados, se reportan defectos y se documentan las lecciones aprendidas.

Técnicas de diseño de pruebas

Caja negra

Se prueba el comportamiento del software sin conocer su código interno, solo entradas y salidas.

Caja blanca

Se diseñan casos conociendo la estructura interna del código, buscando cubrir sus rutas lógicas.

Caja gris

Combina ambos enfoques: algo de conocimiento interno junto con pruebas orientadas al usuario.

Herramientas comunes

  • JUnit / NUnit: frameworks para pruebas unitarias en Java y .NET.
  • Jest: testing unitario y de integración para JavaScript.
  • Selenium / Cypress: automatización de pruebas end-to-end sobre navegadores.
  • Postman: pruebas manuales y automatizadas de APIs.
  • Jenkins / GitHub Actions: ejecución automática de pruebas en integración continua.

Roles en el equipo de testing

QA Tester

Diseña y ejecuta los casos de prueba, y reporta los defectos que encuentra.

QA Automation

Construye y mantiene los scripts que automatizan pruebas repetitivas.

Test Lead

Planifica la estrategia de pruebas y coordina al equipo de testing.

Desarrollador

Escribe pruebas unitarias sobre su propio código antes de integrarlo.

Ciclo de vida de un defecto

Cuando una prueba falla, el error reportado sigue su propio flujo hasta quedar resuelto:

  • Nuevo: el tester detecta el defecto y lo registra con pasos para reproducirlo.
  • Asignado: un desarrollador lo toma para investigar la causa.
  • En corrección: se modifica el código y se prepara una nueva versión.
  • Re-testeo: el tester vuelve a ejecutar el caso para confirmar la corrección.
  • Cerrado: el defecto queda resuelto y verificado.
